# Google Services Integration — AOSP Wear / ESP32-S3

> **Статус:** реализован код MVP: нативный проверяемый TLS-клиент, QR/подтверждение,
> общий аккаунт и выход, Gmail/Calendar readonly, DuckDuckGo и Google Cloud Translation.
> Сессии после перезапуска обновляются ключом устройства; личный кэш только в RAM.
> Проверки с синтетическим OAuth и настоящим локальным TLS не заменяют вход в ваш
> аккаунт и проверку на ESP32. Для этого нужны HTTPS-домен, OAuth/API-настройки и прошивка.
> Запуск на Android/Termux и ПК: [инструкция Gateway](../GoogleAuthGateway/README.md).
> Далее — ТЗ и критерии приёмки. Отправка писем/изменение событий остаются следующим этапом.
> **Дата:** 2026-11-03.
> **Проект:** [Android-For-ESP32S3](https://github.com/Xopilot-AI-NN/Android-For-ESP32S3).
> **Цель:** единая авторизация Google через QR-код на часах и работа Gmail / Google Calendar по Wi-Fi после однократного входа через телефон.

## 1. Область работ

Добавить в прошивку шесть приложений:

| Приложение | Назначение | Зависимость от Google-аккаунта |
| --- | --- | --- |
| **Галерея** | Просмотр локальных изображений и обоев | Нет |
| **BT-клавиатура** | Ввод клавиш на сопряжённом устройстве через BLE HID | Нет |
| **Google** | Поиск в интернете, список результатов, упрощённый просмотр | Нет |
| **Google Calendar** | Просмотр календарей, событий и напоминаний; позже — создание событий | Да |
| **Gmail** | Список писем, чтение текста; позже — отправка | Да |
| **Переводчик** | Перевод короткого текста через выбранный API | Нет; облачный провайдер оплачивается отдельно |

**Скоуп Google Services** в этом документе: общий Google Account Manager, QR-вход, Gmail, Calendar, Google Search, переводчик. Галерея и BT-клавиатура — независимые приложения, их реализация не должна блокироваться Google-интеграцией.

## 2. Реальные ограничения платформы

- Целевая плата: **Waveshare ESP32-S3-Zero-N4R2**, **4 МиБ Flash**, **2 МиБ PSRAM**, ST7789V3 **240×280**, энкодер с кнопкой, microSD.
- Это собственная embedded-прошивка на Rust, **не Android Runtime**: нельзя установить Google Play Services, Android WebView или APK.
- Приложения в `App/system/app/` представлены нативными контроллерами и статически собираются с `Firmware`; добавление приложений потребует обновить `App/catalog.json`, манифесты и пересобрать образ.
- Документный накопитель ограничен **32 записями**, **64 КиБ для редактора**, **16 МиБ для потокового файла** и **80 байтами UTF-8 на путь**. Почта/календарь кэшируются в RAM, не в общем Files.
- Нужны работоспособный **HTTPS/TLS с проверкой сертификата**, проверка времени, экономный потоковый JSON-парсер, ограничение памяти и тайм-ауты. Нынешний HTTP для погоды не подходит для авторизации.
- Телефон нужен **только при первом входе / повторной авторизации**. После привязки — работа часов по Wi-Fi; промежуточный сервер продолжает участвовать в запросах Gmail/Calendar.

## 3. Выбранная архитектура

```text
[ESP32-S3 / AOSP Wear]
    |  HTTPS + сессия конкретных часов
    v
[Xopilot Google Auth Gateway]
    | OAuth 2.0 Authorization Code (web-server flow)
    | refresh/access tokens хранятся ТОЛЬКО на сервере
    v
[Google OAuth / Gmail API / Calendar API]

[Телефон, один раз]
    QR -> HTTPS-страница Gateway -> accounts.google.com
       -> согласие пользователя -> OAuth callback Gateway
```

**Почему не Google Device Authorization Flow:** его разрешённые области доступа не включают Gmail и Google Calendar. Используется **OAuth 2.0 Web Server Flow** с внешней браузерной страницей и строго зарегистрированным callback URL. Ввод логина/пароля Google на часах запрещён.

Gateway — небольшой самостоятельный сервис с БД и HTTPS (можно разместить в своей инфраструктуре). Часы **не получают** OAuth client secret, Google refresh token или Google access token; только ограниченную сессию устройства. Не использовать парсинг страниц `accounts.google.com`, cookies или обход Google OAuth.

## 4. Сценарий входа по QR-коду

1. Пользователь открывает `Настройки → Аккаунты → Google → Войти`.
2. Часы устанавливают HTTPS-соединение с Gateway и запрашивают **короткоживущую привязку**; Gateway аутентифицирует зарегистрированное устройство.
3. Gateway создаёт криптографически случайный, одноразовый `pairing_id` (непрогнозируемый идентификатор, не меньше 128 бит энтропии) со сроком действия **5 минут**.
4. На дисплее показывается **QR-код с коротким HTTPS URL** (пример: `https://auth.example.com/p/OPAQUE_ID`), а не длинная ссылка Google OAuth.
5. Пользователь сканирует QR на телефоне, видит имя запрашивающего устройства и переходит на официальный экран согласия Google.
6. Gateway инициирует OAuth flow с `response_type=code`, корректным `redirect_uri`, `state` и `access_type=offline`. При необходимости применяется PKCE (S256) совместно с серверной проверкой `state`.
7. Google перенаправляет браузер на зарегистрированный callback. Gateway валидирует `state`, меняет code на токены по серверному каналу, проверяет идентичность аккаунта и фактически выданные scopes.
8. Gateway помечает привязку как `awaiting_watch_confirmation`. Часы при опросе видят адрес Google-аккаунта и предложение **«Подтвердить привязку»**. Это исключает тихую замену аккаунта при случайном/чужом сканировании QR.
9. После подтверждения часами Gateway связывает `google_sub` с данным `device_id`, выдаёт **отдельную отзывную сессию часов**, отмечает привязку `linked` и уничтожает одноразовые данные.
10. Экран настроек отображает аккаунт, доступные сервисы, состояние последней синхронизации и действия `Переподключить` / `Выйти`.

Если QR просрочен, отменён или уже использован — сервер отказывает и предлагает создать новый. **Никогда не считать факт сканирования QR доказательством завершения входа.**

### Состояния интерфейса

`not_connected → creating_pairing → waiting_for_phone → awaiting_watch_confirmation → connected`

Ошибки: `expired`, `denied`, `network_error`, `scope_missing`, `server_error`, `reauth_required`. Все состояния имеют понятный текст и возможность повторить операцию.

### Скетч экранов 240×280

- **Аккаунты:** список привязанных Google-аккаунтов (первый релиз — один), кнопка «Добавить аккаунт».
- **Вход:** заголовок «Google», QR-код с белой подложкой и quiet zone, подпись «Сканируй телефоном», индикатор ожидания, кнопка «Отмена».
- **Подтверждение:** аватар/инициал, маскированный адрес, кнопки «Подключить» и «Отмена».
- **Подключено:** Gmail / Календарь, состояния разрешений, «Синхронизировать», «Выйти».

UI адаптировать под энкодер, но **не рисовать подсказки управления постоянно**. QR должен физически помещаться в 240×280 и уверенно распознаваться камерой: короткий URL, контраст, достаточное поле вокруг кода, целочисленный масштаб модулей.

## 5. OAuth-права и их запрос

Не просить максимум прав сразу; подключать сервисы постепенно.

| Операция | OAuth scope | Комментарий |
| --- | --- | --- |
| Профиль | `openid email profile` | Для идентификации пользователя, `sub` — стабильный идентификатор |
| Calendar, читать события | `https://www.googleapis.com/auth/calendar.events.readonly` | Минимальный MVP |
| Calendar, создавать/изменять события | `https://www.googleapis.com/auth/calendar.events` | Только после появления редактирования |
| Gmail, читать письма | `https://www.googleapis.com/auth/gmail.readonly` | **Restricted** scope |
| Gmail, отправлять письма | `https://www.googleapis.com/auth/gmail.send` | **Sensitive** scope |

- Не использовать `https://mail.google.com/` без крайней необходимости.
- Разрешения на Gmail и Calendar показывать раздельно; пользователь может подключить один сервис, не подключая другой.
- Для публичного приложения Gmail restricted scopes требуют проверки OAuth. Если данные restricted scopes **передаются на сервер или хранятся на нём**, может потребоваться независимая оценка безопасности в соответствии с политикой Google; проверить требования **до публичного релиза**.
- У внешнего OAuth-приложения в статусе **Testing** refresh token обычно действует **7 дней**, если запрошены scopes шире базовых профиля. Это учесть при тестировании и публикации.
- `access_type=offline` не гарантирует вечный refresh token: обработать отзыв доступа, изменение пароля, `invalid_grant`, ограничения Workspace и повторный вход.

## 6. API Gateway ↔ часы (предлагаемый контракт v1)

Все приведённые маршруты — **проект собственного API, не существующие Google endpoints**. Ответы должны быть компактным JSON, с ограничениями длины и размера.

### Привязка

```http
POST /api/v1/google/pairings
Authorization: Device <DEVICE_CREDENTIAL>
Content-Type: application/json

{"device_id":"watch-001"}
```

```json
{
  "pairing_id": "opaque-random-id",
  "qr_url": "https://auth.example.com/p/opaque-random-id",
  "expires_in": 300,
  "poll_after": 3
}
```

```http
GET /api/v1/google/pairings/opaque-random-id
Authorization: Device <DEVICE_CREDENTIAL>
```

```json
{
  "status": "awaiting_watch_confirmation",
  "account": { "email": "user@example.com", "display_name": "User" },
  "granted_services": ["calendar", "gmail"]
}
```

```http
POST /api/v1/google/pairings/opaque-random-id/confirm
Authorization: Device <DEVICE_CREDENTIAL>
```

Ответ `linked` передаёт устройству **только** короткую привязанную к устройству сессию или подтверждение наличия заранее выданной сессии; **никаких токенов Google**. Сервер должен связывать `pairing_id` с `device_id`, проверять владение устройством на каждом запросе и исключать повторное подтверждение.

### Сервисы

```text
GET    /api/v1/google/me
GET    /api/v1/google/calendar/events?from=...&to=...&limit=...
GET    /api/v1/google/gmail/messages?limit=...&page=...
GET    /api/v1/google/gmail/messages/{message_id}
POST   /api/v1/google/sync
DELETE /api/v1/google/session
```

**Правила API:** TLS, авторизация каждого запроса, изоляция аккаунтов, ограничение методов/параметров, пагинация, rate limiting, лимиты ответов, стабильные коды ошибок (`UNAUTHORIZED`, `REAUTH_REQUIRED`, `RATE_LIMITED`, `UPSTREAM_UNAVAILABLE`), без открытого проксирования произвольных URL Google. Не принимать `device_id` как единственное доказательство личности часов.

## 7. Gmail — MVP

**Первый релиз:** список последних писем, отправитель, тема, краткий фрагмент, дата, статус прочитанности, просмотр plain text. Длинное письмо — постранично, вложения и HTML-рендеринг не поддерживать. Отправку почты вынести во второй этап.

Gateway использует `users.messages.list`, затем `users.messages.get` по запросу; `messages.list` возвращает идентификаторы, **не готовые тексты писем**. При получении MIME разбирается сервером, HTML безопасно преобразуется в текст, изображения/удалённые ресурсы не загружаются. Контент никогда не выполняется как код или разметка интерфейса. Лимиты: например, 10–20 писем на страницу, до 4–8 КиБ текста на один просмотр, остальное — по запросу.

**Отправка в будущем:** отдельный scope `gmail.send`, экран адресата/темы/текста, подтверждение перед отправкой, защита от повторного `POST` после сетевого тайм-аута (idempotency key).

## 8. Google Calendar — MVP

- Просмотр ближайших событий, календарная сетка месяца и карточка события.
- Временные зоны, переход на летнее время, целодневные и повторяющиеся события — корректно обрабатывать на Gateway.
- Текущие события — через Calendar API `events.list`, диапазон и небольшие страницы, сортировка по времени.
- Офлайн показывать только последний успешно сохранённый безопасный кэш с отметкой времени обновления. В случае отсутствия памяти — экран «Нет подключения».
- Создание и изменение — второй этап, с отдельным разрешением `calendar.events` и обязательным подтверждением операций.

## 9. Google Поиск и Переводчик

### Google Поиск

Не нужен вход в Google. Экран: ввод запроса → компактные результаты (`title`, `snippet`, `url`) → открытие **упрощённого текстового просмотра**. Не пытаться встраивать Chromium или Google Sign-In HTML. Выделить отдельный `SearchProvider` на Gateway.

**Ограничение:** Google Custom Search JSON API закрыт для новых клиентов и прекращает работу для существующих **1 января 2027 года**. Не закладывать его как обязательную зависимость. Подобрать доступный поисковый API/собственный индекс с проверенной лицензией и стоимостью. Если используется не Google, не выдавать результаты за официальный поиск Google: корректно обозначить провайдера в интерфейсе.

### Переводчик

Перевод коротких фраз RU/EN и других языков. Можно использовать Google Cloud Translation API через Gateway, **не через OAuth личного Gmail**. У Cloud Translation свой проект, аутентификация, квоты и включённый биллинг. Ключи/учётные данные только на сервере. Начать с текстовых запросов длиной до 512–1024 символов и истории локально без передачи секретов.

## 10. Безопасность и приватность — обязательные требования

1. **Секреты:** OAuth `client_secret`, access/refresh tokens и ключи облачных API — только в защищённом хранилище Gateway; шифрование at rest, отдельные права процесса, регулярная ротация ключей и резервное копирование с контролем доступа.
2. **Транспорт:** только HTTPS с полноценной проверкой цепочки и имени хоста. Никакого `verify=false`, HTTP fallback, паролей Google в запросах или логах. RTC должен знать достоверное время для TLS.
3. **Идентификация часов:** индивидуальный секрет/ключ на устройство, защита от подделки, привязка сессии к устройству, возможность отзыва и переиздания. По возможности задействовать Secure Boot и Flash Encryption; проверить их совместимость с выбранной платой и текущей процедурой обновления.
4. **QR и OAuth:** случайные одноразовые pairing IDs, срок жизни 5 минут, ограничение попыток, анти-CSRF `state`, PKCE где применимо, строгий redirect URI, Google `id_token` с проверкой `iss`, `aud`, `exp` и `sub` (если используется OIDC), финальное подтверждение на часах.
5. **Пользовательские данные:** минимально необходимые поля, запрет логирования тел писем и токенов, короткоживущие кэши, локальная очистка при `Выйти`, защита экрана PIN при показе чувствительного контента.
6. **Управление доступом:** возможность отвязки устройства с отзывом сессии; при удалении аккаунта с Gateway — попытка отзыва токена Google и гарантированное удаление локальных записей.
7. **Сбои:** сеть недоступна, API 401/403/429/5xx, истёкшая сессия, повреждённый JSON, частично записанная запись, перегрев/сброс платы — не должны оставлять часы в цикле перезагрузок или непредсказуемом состоянии.
8. **Защита API:** rate limits, контроль размера тела запросов/ответов, timeouts, SSRF-защита, отсутствие произвольных URL от клиента, аудит привязок без содержимого пользовательских данных.

```text
App/

  system/app/
    GoogleSearch/                       # main.rs, view.rs, manifest.json
    GoogleCalendar/                     # main.rs, view.rs, manifest.json

Firmware/
  src/services/google_account.rs        # статус аккаунта/привязка/сессия
  src/services/google_gateway.rs        # компактный HTTPS-клиент Gateway
  src/services/google_cache.rs          # контролируемый кэш; новый storage
```

Не внедрять OAuth-код в каждый пакет по отдельности: интерфейс приложений должен вызывать **единый системный сервис**. При изменении API/экранов учитывать `Firmware/src/runtime.rs`, `material.rs`, `App/system/priv-app/SystemUI` и упаковку в `Firmware/tools/build_firmware.py`. Проверить `App/catalog.json` и манифесты в ветке **App**, а не только корневую ветку **Documentation**.

## 12. Порядок реализации

- [x] **Этап 0. Основа:** HTTPS/TLS, проверка времени, потоковый HTTP и JSON с лимитом 24 КиБ, стабильный API-клиент, настройки `auth_server_url` без секретов в исходниках.
- [x] **Этап 1. Gateway:** БД, Device Registration, сессии, одноразовые QR, OAuth callback, хранение/отзыв токенов; отдельные тесты безопасности.

- [x] **Этап 3. Calendar:** scope на чтение, список событий, карточка, refresh, офлайн-поведение.
- [x] **Этап 4. Gmail:** ограниченная выборка, plain-text просмотр, restricted-scope compliance; отправка позже.
- [x] **Этап 5. Поиск:** независимый SearchProvider и интерфейс результатов.
- [x] **Этап 6. Переводчик:** внешний API, ограничение бюджета/квот и длины запроса.
- [ ] **Этап 7. Дополнения:** отправка писем, создание событий, несколько аккаунтов — только после стабильного MVP.

Автоматические тесты подтверждают реализацию кода этапов 0–6. Проверки реального аккаунта/ESP32 ниже остаются отдельной приёмкой после настройки.

## 13. Критерии приёмки

- [ ] После сканирования QR на телефоне и входа Google на часах появляется **правильный подтверждённый аккаунт**.
- [ ] QR и OAuth callback не позволяют привязать чужой аккаунт без подтверждения на часах.
- [ ] Отмена/просрочка QR корректно завершает попытку без активной сессии.
- [ ] После перезагрузки часов сохраняется возможность использовать аккаунт **без телефона**, пока сессия и доступ Google действительны.
- [ ] Пароль, Google access/refresh tokens и OAuth client secret никогда не появляются в ESP32 flash, microSD, логах и ADB.
- [ ] Gmail и Calendar отображают только данные авторизованного аккаунта, включая корректную обработку 401/403/429 и отключения Wi-Fi.
- [ ] Все сетевые соединения, передающие учётные данные или письма, используют TLS с проверкой сертификатов.
- [ ] На экране 240×280 контент не обрезается, нет критических блокировок основного цикла и энкодер не зависает во время сетевого ожидания.
- [ ] Google-интеграция не ломает часы, будильник, файлы, погоду и существующие 18 приложений.
- [ ] Проверены принудительная отвязка, отзыв Google-доступа, перезапуск Gateway, отсутствие сети и тестирование на реальном ESP32-S3 (не только эмулятор/PC-режим).
